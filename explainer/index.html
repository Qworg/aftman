Design explainer

aftman — software that watches the software

Aftman puts a small, fast judgement model above a slower coding agent. The agent writes the code. Aftman watches it work, decides whether it is actually succeeding, and intervenes when it is not.

01The problem

Modern coding agents are good at writing code and bad at knowing when to stop. If you hand one a task and walk away, you eventually have to answer the same questions yourself:

🔁

Is it stuck?

It has re-run the same failing test four times with tiny variations. That looks like work. It is not.

🎯

Is it still on the job?

You asked for a bug fix. It refactored the logging layer, the test helpers, and the CI config.

✅

Is it actually done?

It says "all tests pass". It did not run the tests. You find out in review, or in production.

The real bottleneck

The agent's work is fast and cheap. Watching it is the slow part, and today the watcher is you. You supervise by reading a diff after the fact — which is the most expensive possible moment to find a problem.

Aftman is an attempt to automate the watching without automating the work. It does not choose files or write code. It observes, judges, and intervenes.

02The idea

Split the job in two. A coding agent does the engineering. A separate supervisory loop asks narrow, repetitive questions about what is happening — and answers them cheaply enough to run continuously.

🧠

A decision model, not a chat model

Aftman asks Jev (TypeSafe's System One model) questions like "is this worker stuck?". It gets back a probability — a number between 0 and 1 — not a paragraph. Ten questions go out in one request and come back independently.

⚖️

Plain code decides

The probabilities go to ordinary, deterministic Rust that compares them to thresholds and picks exactly one action. The model estimates. The code acts.

👀

Bounded evidence

Nobody dumps a repository into a model. Aftman sends a small, size-capped summary: git status, part of the diff, the tail of the agent's output, parsed test results.

Why a probability instead of "yes"

Because "we are 40% sure the tests are adequate" is a genuinely different situation from "we are 95% sure", and a system that flattens both to "no" throws away the information it needs to decide between keep going, verify it, and ask a human.

03How it fits together

Two loops run at the same time. Critically, the supervisor does not stop the agent in order to think — the agent keeps working while it is being judged.

The two loops share nothing except a one-way event stream. That separation is the whole point: the agent cannot talk the supervisor into anything, because the supervisor is not part of the agent's conversation.

04One round of supervision

Aftman repeats this loop every few seconds while the agent works. The agent is never paused for it.

  1. Something happens

    The agent prints output, finishes a tool call, exits, or nothing at all happens for 30 seconds and a timer fires. All three are valid reasons to think.

  2. Skip if nothing changed

    Aftman compares a fingerprint of the situation to last time. Identical? No model call, no cost. This is what stops a long silent test run from burning the supervision budget.

  3. Gather bounded evidence

    A size-capped summary is assembled: the job, the status, the agent's recent output, a trimmed diff, untracked new files, parsed test results.

  4. Ask the model

    All active questions go out in one request. Each comes back as a probability: implementation_complete 0.91, worker_stuck 0.02.

  5. Turn probabilities into proposals

    Each area of responsibility compares its own numbers to its own thresholds and proposes something — "stop the worker", "verify independently", "nothing to do".

  6. Pick exactly one action

    Deterministic rules discard anything that violates a hard limit, then take the most conservative surviving proposal. Every proposal and every rejection is recorded.

  7. Act, then write it down

    Steer the agent, stop it, spawn an independent verifier, finish, or ask a human. The result is persisted before the next round starts.

Why this is auditable

Step 6 is a pure function: the same inputs always produce the same action. Combined with an append-only event log, that means any run can be replayed offline and the question "why did it do that?" is always answerable after the fact.

05How a number becomes an action

This is the part worth understanding. A probability is compared to a threshold — but a probability that lands right next to its threshold tells you almost nothing. Acting on it is a coin flip wearing a number.

The rule in one sentence

A rule fires only when its number is on the right side of the threshold and far enough from it to be believed. A second opinion can take permission away and can never give it.

Disagree with the model and the action is cancelled. Agree with it and nothing changes — agreement is not a licence. That asymmetry is intentional, and the next section is about why.

06Three safety rules

Everything above is a mechanism. These are the properties the mechanism is built to guarantee, stated the way you would state them to a colleague.

1 · The model estimates. Plain code decides.

No model output ever becomes an action directly.

Every action depends on things a model cannot know: how many attempts remain, whether a verifier has already run, whether the overall timeout has expired. Those live in ordinary code. The model supplies a number; the code decides what that number is allowed to do.

2 · A second opinion can stop work. Only evidence can finish it.

An opinion may veto. It may never approve.

Finishing a job is the one irreversible action. So it is the one action no model opinion can cause. An opinion that says "looks done" is treated as noise. An opinion that says "looks wrong" is allowed to stop, verify, or escalate.

To actually finish, aftman has to go and measure: run the repository's tests itself, then re-ask the model with the fresh results.

3 · Uncertainty blocks. It never accelerates.

"I don't know" always resolves to the more cautious option.

If any check ends up in the band and nobody can resolve it, aftman refuses to declare the job finished — even if every other number looks great. This matters more than it sounds: without it, a check that should block completion is disarmed precisely when its own measurement becomes uncertain, and the run finishes on a technicality.

And one rule about credentials

Not negotiable

The API key that pays for the supervisor is stripped from the agent's environment before the agent is launched. A coding agent has a shell. If it can read the key, then any text it reads from anywhere can leak it. The agent authenticates itself, with its own login, and never sees the supervisor's.

The most common real failure, start to finish. No second model is involved anywhere in this story — which is rather the point.

The interesting part

The agent's 3 passed claim was about text. The model was asked to judge that text, and it did — plausibly. The system's response to a plausible-but-unverifiable answer was not to ask a different model. It was to go and run the tests. Making more evidence beats asking another model to guess about thin evidence.

08How you use it

One core process owns the runs and emits one stream of events. Everything else is a client of that core — so you can watch the same run from a terminal, from a browser, or from inside a terminal multiplexer, and none of them is required.

What it looks like on the command line

# hand it a job
aftman run --repo ./my-project --job "Add request retries with backoff and tests"

# which agent does the work
aftman run --repo . --job "..." --worker pi      # or agy, claude

# watch a run, live
aftman watch <run-id>

# why did it do that?
aftman decisions <run-id>

And when it does the interesting thing

Once in a while aftman will decide it genuinely cannot tell, and stop to ask you. That is a goal of the system, not a failure of it — the alternative is a confident guess. The question and everything it knows arrives in whichever surface you are using, and the run waits.

09What it is not

A design that does not say what it refuses to do is not a design.

It is

  • A supervisor. It observes an agent, judges its progress, and intervenes.
  • Agent-agnostic. The same supervision works over different coding agents behind one small interface.
  • Auditable. Every probability, proposal, rejection, and action is in a log you can replay.
  • Honest about uncertainty. "Ask a human" is a first-class outcome.
  • Local-first. It runs on your machine, and remote access is a deliberate choice you make.

It is not

  • A coding agent. Aftman never edits your code. Something else does that.
  • A sandbox. It does not confine what an agent can touch. Use a container or a throwaway checkout for untrusted jobs.
  • A guarantee. Calibration is not correctness. This reduces the chance of a wrong call. It does not remove it.
  • A replacement for review. It makes the diff smaller and the failures louder.
  • An orchestrator of many agents. One worker at a time, by design — every question above assumes a single active worker.
The honest caveat

The central bet is that asking a small decision model narrow questions is fast and cheap enough to run continuously alongside a much slower agent. That bet is the reason the design looks like this — and it is a claim that should be measured in your environment, not taken from a diagram.
